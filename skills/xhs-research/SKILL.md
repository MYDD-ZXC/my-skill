# 小红书爆文爆品调研

核心原则：**顺序不能反**。先判断赛道有没有成交承接，再找爆文。
在直播占 88% 销售额的类目里找爆文，等于在没水的地方打井。

## 🔴 通道铁律：调研一律走云手机，禁止 Web 自动化

**2026-10-26 实战事故**：用 Playwright 驱动浏览器抓小红书搜索页与笔记详情，短时间翻多篇笔记，
**触发了平台风控——账号异常，浏览器被强制关闭**。

### 为什么 Web 自动化更危险

| 维度 | Web（Playwright/CDP） | 云手机（App + ADB） |
|---|---|---|
| 设备指纹 | 桌面 Chrome + CDP 调试端口，**可被识别** | 真实 Android 设备、真实 App |
| 行为特征 | 无鼠标轨迹、翻页节奏机器化 | 真实触摸事件，节奏可控 |
| 登录态 | 直接暴露主号 Cookie | 独立设备 + 独立 IP + 独立登录 |
| 请求频率 | 一次详情页 = 一串 XHR，容易触发频控 | 一次点击 = 一次正常页面加载 |
| 被封代价 | **封主号**，店铺权重一起没 | 封小号，换设备即可 |

### 硬规则

1. **所有站内采集（搜索/笔记/详情/评论/商品）只用云手机 ADB 通道**
2. **禁止**用 Playwright、CDP、Selenium、requests 直连小红书任何页面
3. Web 端只允许一种用法：**用户自己打开页面，Agent 被动读取**（此时不算自动化）
4. 乘风/千帆后台是**自家数据**，不受此限（但仍然低频、人工节奏）
5. 一旦出现验证码 / 滑块 / "账号异常" / 302 到 `/404/sec_xxx`：**立即停止全部操作，24 小时内不再登录**

### 账号隔离（重要前提）

**风控是按账号算的，不是按设备算的。** 本项目当前配置：

| 通道 | 账号 | 封了影响 |
|---|---|---|
| Web 自动化 | **主号**（绑店铺，873 篇历史权重） | 灾难级，绝不冒险 |
| 云手机 App + ADB | **独立小号**（与主号不同账号） | 换台机器即可 |

因此：
- **Web 自动化 = 永久禁止**（主号不能碰）
- **云手机 = 可正常使用**，但仍受节奏限制（每词 ≤8 屏、词间隔 ≥15s、详情 ≤5 篇）
- 云手机若被封：只损失小号，**但不要在同一台云手机上再登主号**（会关联）


### 事故后的恢复动作

```
① 立刻关闭所有自动化浏览器进程
② 24~48 小时内不要用该账号登录 Web 端，只用手机 App 正常刷（模拟真人使用）
③ 检查站内消息是否有违规通知，有则按提示申诉，不要反复提交
④ 若只是流量下滑：保持 7 天正常发布节奏，不要突然停更
⑤ 复盘：这次的入口 URL、频次、翻页数，写进事故记录
```


## 五层漏斗

| 层 | 回答什么 | 数据源 | 频率 | 成本 |
|---|---|---|---|---|
| **L1 赛道** | 靠直播还是靠笔记成交？ | 乘风·类目洞察 → 成交载体 | 月更 | 0 |
| **L2 商品** | 哪些品在卖、价格带、集中度 | 乘风·商品洞察 100 条 / 云手机「商品」Tab | 周更 | 0 |
| **L3 爆文** | 哪些是爆款、怎么爆的 | 站内搜索（最多点赞 / 最多收藏 + 时间窗） | 日更 | 0 |
| **L4 内容** | 挂了什么品、观众买不买 | 笔记详情页 + 评论区（需 xsec_token） | 日更 TOP10 | 0 |
| **L5 商品** | 价格 / 已售 / 上新 / 商品ID | **云手机 App（唯一能拿到）** | 周更 | 设备费 |

**硬规则**
- 直播销售额占比 **>70% → 直接弃赛道**，不必再看内容层。
- L3 第一排序用**最多收藏**，不是最多点赞。收藏是比点赞更准的购买前置信号（实测 收藏→单转化率是 赞→单 的 3 倍）。
- L4 只核验 TOP5 爆文，不做全量。

## L1/L2：乘风后台（零风险，最权威）

入口 `chengfeng.xiaohongshu.com` → 数据 → 类目洞察 / 商品洞察。

抓三样：
1. **成交载体**（直播 / 笔记 / 商卡 的销量与销售额占比）← 决定要不要做
2. **综合得分榜**（同类目下各子类目排序，看哪个细分在上升）
3. **商品洞察 100 条**（含价格区间）→ 算头部集中度：TOP10 销量占比

## L3：站内搜索（Web 端，最便宜）

**关键限制：网页端"发布时间"只有 一天内 / 一周内 / 半年内 三档，没有 7/15/30 日。**
所以做法是：按「最多点赞」抓 → 读每篇发布日期 → 自己切 7/15/30 天桶。

URL 参数（筛选面板用 JS 点不稳，直接拼 URL 最可靠）：

```
https://www.xiaohongshu.com/search_result?keyword=<urlencode>&type=general&sort=popularity_descending
```

**判定阈值**

| 档位 | 条件 | 用途 |
|---|---|---|
| 爆款 | 赞 ≥1000 且 ≤30 天 | 对标 / 拆结构 |
| 潜力 | 赞 ≥300 且 ≤15 天 | 优先复刻 |
| 新鲜 | ≤7 天 且 赞 ≥100 | 早期信号，即时跟投 |

**爆款密度 = 30 日内达标篇数 / 该词总采集篇数。** 密度高 = 红海，密度低 + 平台说紧缺 = 洼地。

## L4：笔记详情与评论区（Web 端，带 token 可进）

裸 `/explore/<id>` 会 404（error_code 300031）。**必须带 `xsec_token`**，从搜索结果卡片的 `<a href>` 里取：

```
/search_result/<note_id>?xsec_token=...   → 自动 302 到 /explore/...
```

能拿到：点赞 / 收藏 / 评论全文 / 作者回复话术 / 商品名（**纯文本，无链接**）。

**意向密度** = 含购买意图的评论数（多钱/怎么买/有链接吗/能机洗吗）/ 总评论数。
>25% 说明这个内容真的在承接需求，不是纯审美自嗨。

## L5：云手机 ADB（拿 Web 拿不到的那层）

Web 端拿不到商品卡，`?type=goods` 搜索返回空页。只有 App 里能拿到**价格 / 已售 / 商品ID / 上新时间**。

### 前置
1. 红手指 PC 客户端 → 右键云手机 → **ADB 调试** → 建立连接 → 得到 `127.0.0.1:<端口>`
2. `adb connect 127.0.0.1:<端口>`，`adb devices` 显示 `device`（不是 unauthorized）
3. 装 ADBKeyboard（中文输入必需，`adb shell input text` 不支持中文）

### 已验证的设备事实（红手指 VIP / Android 13）
- 分辨率 **720×1280，density 320**
- 包名 **`com.xingin.xhs`**
- 商品详情页 Activity：`com.xingin.commercial.goodsdetail.v2.activity.GoodsDetailActivityV2`
- `uiautomator dump` **文字可读**（182 节点 / 34 有文字），非自绘空文本
- **商品卡关键字段合并在一个 TextView**：`券后¥8.99已售6.7万+` → 一条正则同时解出价格和销量

### 捷径：商品详情页的「推荐」Tab 可以滑，但**不能当品类采样器**
一屏 4 个商品，每个带「券后价 + 已售 + 标题 + 店铺 + 点赞」，下滑无限加载。

**实测踩坑（2026-10-26，滑 12 屏 19 个样本）**：这个信息流是**算法全局推荐**，不是同品类。
牛奶绒商品详情页的「推荐」里，出现的是手机壳、粉底液、香薰、餐具盲盒——家纺只占 3/19。
价格分位被拉成 P10=8.9 / 中位=21.8 / P90=129，**完全不能代表四件套的价格带**。

**正确用法**：
- 「推荐」Tab → 只用来观察**跨品类的消费趋势**（什么价位段在爆），不做单品类分析
- 单品类竞品采样 → **搜索 → 切「商品」Tab → 按「销量」排序 → 再滑**（这才是按类目聚合的）

### 状态判定（比截图快）
```bash
adb shell dumpsys window | grep mCurrentFocus
```
返回 Activity 名即可判断在哪个页面，用于流程校验与异常恢复。

## 工具

本 skill 配套脚本在 `<workspace>/xhs-automation/tools/`：

| 文件 | 作用 |
|---|---|
| `adb/platform-tools/adb.exe` | 便携版 adb，不污染系统 PATH |
| `xhs.js` | 主驱动器：连接 / 快照 / 按文字点击 / 输入 / 滑动 / 采集 |
| `run.bat` | 双击启动。默认 watch 模式：**监听 `data/cmd.json`，一变就执行** |
| `probe-adb.bat` | 一次性探测：连接 + 分辨率 + 前台包名 + 元素树 + 截图 |
| `ui.bat` | 一键快照：dump + pull + parse |
| `setup-ime.bat` | 下载并安装 ADBKeyboard（中文输入） |
| `parse-ui.js` | 解析 ui.xml → `data/ui-nodes.txt`（多行可读） |

### 指令协议（cmd.json）

```json
{"seq": 7, "action": "tap", "text": "商品"}
```

| action | 参数 | 说明 |
|---|---|---|
| `snap` | - | dump 元素树 + 截图，写 `ui-nodes.txt` / `adb-shot.png` |
| `tap` | `text` | 按文字找控件并点中心（优先可点击节点） |
| `tapxy` | `x`,`y` | 按绝对坐标点 |
| `swipe` | `dir`(up/down), `n` | 滑动 |
| `search` | `text`, `tapSearchBox`(可选) | 点搜索框 → 输入 → 回车 |
| `collect` | `rounds`, `prefix` | 在推荐流里滑 N 屏采集商品卡 → csv + 汇总 txt |
| `input` / `key` / `shot` / `state` | - | 基础能力 |

执行结果写 `data/result.txt`（JSON：ok / action / ms / focus / output / error）。

### 为什么用「文件指令 + 常驻 watch」而不是直接调用
Agent 的命令执行通道可能不可用（沙箱故障）。文件指令模式让脚本在用户双击后常驻，
Agent 只读写 JSON，不依赖 shell —— **可用性更高，也更容易交给非技术用户使用**。

## 四个必须避开的误用（2026-10-26 实战踩过）

### 1. 只做商品层 = 选不出品
商品层（价格/已售）只证明"这个价格带存在需求"，**证明不了你能吃到**。
一个品卖 3 万单，可能 90% 来自直播、可能是品牌旗舰自营、可能找不到同款货源。
**商品层是必要不充分条件**，最后必须回 L1 看成交载体 + 人工核对货源。

### 2. 站的推荐是个性化的，单次截面不可比
同一搜索词，不同账号看到的商品池不同（受历史购买、地域、消费力影响）。
- ❌ 错：滑一次就下"价格带分布"结论
- ✅ 对：同一词**至少两个时间点**采样对比；或先用**乘风商品洞察**（官方口径、无个性化）做基准，App 只做核验
- 排序用「销量」比「综合」客观（是该 query 下的全站排序），但**召回仍个性化**

### 3. 品牌货不可复刻，必须先判定`羊毛毯` 实测：TOP15 全是旗舰店（赛波斯 4 / ComiComi 3 / 陌希 3），价格 400~2500，销量都不过 2000。
典型"高价低频 + 品牌垄断"，与一件代发不兼容。

**可复刻性判定（按顺序，任一否决即放弃）**

| # | 判定 | 通过条件 | 工具 |
|---|---|---|---|
| ① | **独家性** | 小红书同款 ≥2 个卖家（只有 1 个 = 大玩家独家，跳过） | 识图搜同款 |
| ② | **同款密度** | 2~10 个卖家，且多为近 90 天出现 | 识图 + 发布时间 |
| ③ | **是否旗舰自营** | 非品牌旗舰 / 非独家设计专利 | 店铺页看认证 |
| ④ | **1688 有无同款** | 图搜能命中，且供货价 ×1.4 ≤ 该品 P75 | 1688 以图搜货 |
| ⑤ | **是否依赖直播** | 回 L1 看成交载体，直播 ≤70% | 乘风类目洞察 |

### 3.1 同款密度：判断"能不能进"还是"已经打烂"
同一品在小红书的卖家数量，决定它是机会还是陷阱：

| 同款卖家数 | 形态 | 判断 |
|---|---|---|
| **1 个** | 独家/品牌自有 | ❌ 放弃（你复刻不了，也没法截流） |
| **2~5 个，多为近期出现** | 窗口期 | ✅ **最佳入场点**（有人验证了需求，但还没打烂） |
| **6~10 个** | 竞争期 | ⚠️ 需要差异化（价格/服务/内容角度） |
| **>10 个，且价格已下探** | 泛滥 | ❌ 放弃，进去就是价格战 |

**注意**：不能只看"有多少家在卖"，还要看**它们是什么时候开始的**。
10 家都是近 30 天冒出来的，说明需求刚被验证、正在扩散；10 家都做了一年，说明已经打透了。

### 3.0 同款密度必须用 ≥3 个搜索词交叉采集

**实战教训（2026-10-26 斑马纹）**：
- 单搜「斑马纹沙发毯」→ 只看到 **5 家**竞品 → 差点判定"窗口期"
- 补搜「斑马纹 沙发毯」「斑马纹 毛毯」后去重 → **11 家**竞品（严格同款 6 家 + 邻近款 5 家）
- 判定从「窗口期」修正为「**竞争期，需差异化**」

原因：平台召回个性化，单次搜索只暴露部分池子；不同词的覆盖人群也不同。
**只看一次就下"窗口期"，会系统性高估机会。**

做法：
1. 至少 3 个搜索词（`核心词+品类` / `品类+核心词` / `上位品类词`）
2. 每个词单独 collect，导出 csv
3. 合并去重（按店铺名 + 标题）
4. 再数家数、看价格分布


### 3.2 三平台交叉验证（缺一不可）

| 平台 | 回答什么 | 拿到什么 | 风险 |
|---|---|---|---|
| **小红书站内** | 需求真不真、内容能不能做 | 笔记热度、评论区意向、同款密度 | 低（只读） |
| **千帆 / 乘风** | 这个类目靠什么成交 | 成交载体占比、类目大盘、商品洞察 | 零（官方后台） |
| **1688** | 我能不能供货、能不能上架 | 图搜同款、供货价、起订量、是否一件代发 | 低（有账号即可） |

**判定顺序：1688 先过 → 再看乘风载体 → 最后看内容。**
因为供货是第一道硬门槛：1688 找不到同款，后面全白搭。

### 4. 词义歧义直接毁结论
`羊毛毯` 在小红书 = **羊毛地毯**（客单 2000+），不是保暖盖毯。
**开跑前先看 TOP10 标题确认品类形态**，不要相信商机榜的词面意思。

## 判定门槛（不达标不进入下一层）

| 层 | 门槛 | 不达标怎么办 |
|---|---|---|
| L1 | 直播销售额占比 ≤70% | 弃赛道，换词 |
| L2 | 头部 TOP10 销量占比 <60%（有得切） | 换细分，别硬打 |
| L3 | 30 日内爆款 ≥3 篇 | 太少先确认是洼地还是没需求 |
| L4 | 意向密度 >25% | 换内容角度重测 |
| L5 | 可复刻性四问全过 | 放弃 |

## 风控边界（必须遵守）

- 只读公开内容：**不点赞、不收藏、不关注、不评论、不发私信**
- 单次任务 ≤20 个商品详情；操作间隔 1.5~3 秒；单日 ≤2 轮
- 用独立小号 + 云手机（独立 IP + 唯一 IMEI），**不要用绑定店铺的主号**
- 出现验证码 / 滑块 → **立即停止**，不要重试
- 不做"自动发布""自动互动"，小红书对 AI 托管账号有专项打击

## 素材反推链路（内容侧，调研的下游）

调研找到可做的品之后，素材不需要纯 AI 生成，有一条更省力也更真实的链路：

```
1688 商品详情页 → 抓商家实拍图 + 买家评论图
  → 挑"拍得好但不像广告"的那几张（有生活痕迹、有褶皱、有猫）
  → 用识图模型分析构图/光线/主体占比
  → 用图生图改成新场景（换客厅/换光/换配色），商品形态保持
  → 主动打 AI 标识
```

**为什么优先用评论图而不是商家主图**：
商家图是精修"卖家秀"，直接复用会触发"货不对板"疑虑（这是实测转化最高的一类内容的反面）。
评论图自带"买家秀"属性，正好对上 L4 里转化 13%+ 的那类选题。

**同一套图源也可用于淘宝**：淘宝买家秀质量更高、场景更杂，可作为 1688 的补充图源。


## 输出规范

每轮调研产出三件东西，缺一不可：

1. **`compete.csv`** — 商品级原始数据（price, sold, title, shop, likes）
2. **`compete.txt`** — 汇总：价格分位 / 价格带分布 / 销量分档 / 店铺集中度 / 销量 TOP15
3. **结论** — 必须回答三个问题：这个价格带有空档吗？头部集中度能不能切进去？爆款密度是红海还是洼地？

没有第 3 条，前两个只是数据搬运。
